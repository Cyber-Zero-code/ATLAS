# Project ATLAS: Architecture Decision Records (ADRs)

## Status: Stage 1 (Foundation & Security Hardening)

### ADR 001: Tenancy Model and Multi-Org Workspace Isolation
- **Context:** Project ATLAS serves private security service firms (MSSPs, incident-response, and OT-resilience consultancies) that manage infrastructure graphs for multiple client organisations.
- **Decision:** Multi-tenant shared PostgreSQL database with Row-Level Security (RLS) forced on every table. The database is the single source of truth.
- **Tenant Hierarchy:**
  - `organisations.kind` is `standalone`, `firm`, or `client`.
  - A client organisation must reference a `parent_firm_id`.
  - A firm user can access a client workspace *only* if they hold an explicit row in `memberships(user_id, org_id, role)`.
  - The UI presents one active workspace at a time and never merges cross-workspace data.
- **Enforcement:**
  - Composite unique keys `(org_id, id)` on every tenant table.
  - Composite foreign keys `FOREIGN KEY (org_id, parent_id) REFERENCES parent_table(org_id, id)` on all child references. This prevents any child record from pointing to another organisation's parent record at the engine level.

### ADR 002: Authentication & Database-Enforced MFA (AAL2)
- **Context:** Cyber-physical infrastructure telemetry is sensitive. Authentication bypasses or soft UI gates are unacceptable.
- **Decision:** Supabase Auth with TOTP MFA.
- **Rule:** Every RLS policy on every application table strictly requires `(auth.jwt() ->> 'aal') = 'aal2'`. Sessions at assurance level `aal1` (password only, without completed MFA challenge) or `anon` read 0 rows and write 0 rows across all tables and RPCs.
- **Prohibition:** No custom auth, no persona switcher, no mock login, no auth bypass anywhere in code.

### ADR 003: Cryptographic Audit Chain & Tamper Resistance
- **Context:** Regulatory, contractual, and evidentiary requirements demand an unalterable history of operations.
- **Decision:**
  - Audit logging occurs strictly inside PostgreSQL via database triggers on data tables and a `log_event()` function for non-table operations (sign-in, view, export, verification).
  - Actor is derived from `auth.uid()` and verified against `memberships`.
  - Timestamps are generated by the database clock in a fixed UTC ISO-8601 text format.
  - One sequential chain per organisation, protected by transactional advisory locking (`pg_advisory_xact_lock`) on the tenant UUID during appends.
  - `record_hash` is computed as `SHA-256(org_id | seq | timestamp_text | actor_id | actor_role | action | target_type | target_id | correlation_id | payload_hash | prev_hash)`.
  - Database triggers block `UPDATE`, `DELETE`, and `TRUNCATE` on `audit_events`.
  - Verification function `verify_audit_chain(p_org_id)` scans the chain, validates unbroken sequence numbering, verifies genesis `0^64` and chained hashes, and flags the exact sequence and reason if tampering occurs.

### ADR 004: Extension Schema Qualification
- **Context:** Portability and clean schema governance require clear placement of third-party PostgreSQL extensions versus core built-in functions.
- **Decision:** `postgis` is installed in the `public` schema (`geometry`, `ST_*` used unqualified). `pgcrypto` is installed in the `extensions` schema (`extensions.digest`, `extensions.hmac` schema-qualified), while core PostgreSQL functions (`gen_random_uuid`, `encode`, `decode`, `convert_to`) are called unqualified. Every `SECURITY DEFINER` function enforces `SET search_path = public, extensions, pg_temp`.

### ADR 005: Evidence Management & Storage Isolation
- **Context:** Evidence files (configuration snapshots, OT packet captures, incident logs) require verifiable integrity and strict tenant isolation.
- **Decision:** Private Supabase Storage bucket `evidence`. Path convention is `<org_id>/<target_type>/<file_name>`. Storage object RLS policies verify that the first path segment matches the user's authorised organisation ID and that `aal = 'aal2'`.
- **Integrity:** SHA-256 calculated client-side via native Web Crypto (`crypto.subtle.digest`) prior to upload and stored in `evidence` with immutable `custody_events`.

### ADR 006: Language and Claims Governance
- **Decision:** Strictly avoid "forensic", "defence-grade", or "predictive". Use "evidence management". Outputs are review signals with uncertainty. Never attribute actions to named persons or threat actors. No offensive targeting or attack simulation.

### ADR 007: Live Threat Intelligence Feeds Deferred to Phase 2
- **Decision:** Live external CTI feed adapters requiring a server-side proxy (`MISP`, `TAXII_2_1`, `ALIENVAULT_OTX`, `ABUSE_CH`) are explicitly deferred to Phase 2 (`DEFERRED — Phase 2`) because Phase 1 excludes TAXII/STIX feed ingest (`CLAUDE.md`) and has no server-side credentialed CTI proxy, so only local operator-supplied STIX 2.1 / CISA KEV JSON bundle parsing runs without browser requests to external feeds.
